# 04 — Merge installer build infrastructure, then qualify two native Studio installers

**Prerequisites:** [Studio 03](03-base-suite-and-release-candidate.md) merged the provisional candidate/version/pins into `main`, and both upstream libraries have **published** released wheels. The **shared packaging-source PR for this spec is now merged** ([Studio PR #9](https://github.com/darizae/biocall-studio/pull/9)); do not recreate that branch or repeat its work. Follow [VERSION_CONTROL.md](VERSION_CONTROL.md). **Execution order has changed:** first run the *complete local* [Studio 05 base suite](05-final-upstream-release-qualification.md) on the frozen post-packaging `main` SHA, **then** execute this spec's two native OS installer lanes (parallel). The tag/release and cross-repository stale-spec cleanup belong **only to [Studio 06](06-release-and-post-release-cleanup.md)**.

Existing [macOS 06](../06-macos-release-and-installer.md), [Windows 07](../07-windows-release-and-installer.md) and [release process](../../RELEASE_PROCESS.md) include stale “Review placeholder” and heavyweight qualification text. Reconcile their active packaging requirements with this approved reduced scope without losing license, signature, actual installer or safe data ownership obligations.

## A. One packaging PR before source freeze

1. From **post-03 `main`**, create **`release/biocall-v0.1.0a1-installers`**. Implement the shared freezer/bootstrap and both platform-specific packaging configurations, worker dispatch/resource bundling, version/brand references and deterministic native-smoke scripts; avoid editable sibling code paths and untested package versions. Put macOS files and Windows files in clearly separate paths, with a single reviewed dependency manifest.
2. Test packaging configuration, imports, any feasible VM smoke, source resource inclusion and static audits. Open an implementation PR, inspect the diff and dependency/branding/licensing information, then **review and merge this PR to `main`**. Merge any additional source corrections **now**, before freezing.
3. Set **`STUDIO_RELEASE_SHA = main HEAD`** *only after this merge* and record the exact version, published upstream tag commits, wheel hashes and build configuration. **Before either native lane starts**, have [spec 05](05-final-upstream-release-qualification.md) run the ordinary Studio base suite **locally on the owner's Mac, at this same frozen SHA**. This is the one immutable build candidate; no new source commits in either native lane.

## B. Two independent native lanes — parallel only after A **and successful local spec 05**

**macOS native runner:** checkout exactly `STUDIO_RELEASE_SHA`, install exact released wheels, build one BioCall Studio `.app` and `.dmg` including checked-in `assets/branding/icons/icon.icns`, Qt/torch/scientific runtime, public alp-ui fonts and all Train/Detect/Review workspaces and frozen `--worker` modes. Install **outside** the checkout, launch all workspaces, do a small deterministic worker/load/export smoke, restart, check per-user storage outside the bundle and safe uninstall preservation. For public signed distribution, verify Developer ID signature, hardened runtime, notarization/stapling and Gatekeeper with actual credentials. Record native runner/OS, build logs, signing outcome and real artifact SHA-256. **Do not** capture a new generic UI gallery.

**Windows native x86-64 runner:** checkout **the same** `STUDIO_RELEASE_SHA`, install the same verified wheel versions/hashes, create the installable BioCall Studio app and installer with checked-in `assets/branding/icons/icon.ico`, Qt/torch runtime and bundled `--worker` entries. Install outside source, launch all workspaces, perform small worker/load/export/restart/uninstall smoke, verify per-user data preservation and signature if required for distribution. Record native runner/OS, actual installer hash and evidence. Linux-generated binaries or Mac screenshots are **not** Windows qualification.

**Parallel restriction:** build/test on separate native runners but **do not open independent platform source PRs after A**. Both lanes must use the exact same release SHA and approved upstream wheel hashes. If either reveals a source defect, open a focused **`fix/biocall-v0.1.0a1-<issue>`** branch from `main`, review/merge, re-freeze **new** `STUDIO_RELEASE_SHA`, and rebuild/reverify **both** installers. Never combine Mac from one SHA with Windows from another.

## Exclusions and handoff

Existing real Cocoa screenshots under `docs/design/evidence/release-real-data` and `docs/design/evidence/review-correction/native-rv10` are good README material. No compulsory new native capture, physical playback proof, soak, 50k, ≥600-second or large field-data performance run, or full Train→Detect→Review scientific retraining on native installers. Studio 05 owns the **one complete ordinary source suite**.

**GitHub API/VM:** packaging source PRs, metadata, static checks; a GitHub-hosted **Windows x64** runner is a genuine native Windows environment for automated build/install/smoke, not a surrogate Linux VM. **Native Mac and Windows environments:** actual freeze/sign/install/launch/uninstall and user-data checks. The source suite is already a separate **local spec 05 pass**, not part of these lanes. **Done only when:** installer source merged, the local suite passed on the frozen SHA, both OS native installer hashes and genuine minimal smoke evidence exist, and absent signing/GUI/legal gates are explicitly flagged. **No tag or release in spec 04: execute [Studio 06](06-release-and-post-release-cleanup.md) afterward.**

## Windows without a borrowed laptop — remote execution is supported

**Preferred approach:** use a short, manually dispatched **GitHub Actions** workflow in this repository on a genuine Windows x64 hosted VM, e.g. `runs-on: windows-2025` (not `windows-11-arm`). Build/verify the same frozen `STUDIO_RELEASE_SHA` after the local Studio spec 05 suite has passed. The existing `packaging/windows/build.ps1`, `packaging/windows/biocall.spec`, `packaging/windows/biocall.iss` and `packaging/windows/smoke.ps1` are the actual starting point; `.github/workflows/installer-source.yml` is currently **Linux-only packaging preflight**, not a Windows build or installed smoke result.

The remote workflow should:

1. Use `workflow_dispatch` or a narrowly gated release-candidate workflow and a pinned explicit `STUDIO_RELEASE_SHA`. Check out/verify **exactly that SHA** and a clean tree, set up Python 3.12 x64, and obtain/check the published upstream wheel hashes and tagged commits. **Never execute release signing secrets for untrusted PR code.**
2. Ensure **Inno Setup 6** and `ISCC.exe` exist on PATH (install via a pinned, trusted mechanism if absent), along with the frozen PyInstaller/build toolchain; run `packaging/windows/build.ps1` against the native Windows checkout and no editable sibling packages.
3. Install the resulting Inno Setup EXE in that Windows VM **outside the checkout**, run the actual `packaging/windows/smoke.ps1` against installed paths, and supplement it with a small **valid** worker/load/export/restart/uninstall/user-data preservation check. `native_smoke.py` alone currently covers mostly negative worker paths and process startup, and does **not** prove successful scientific work or uninstall. Every claim must have real process/log/exit evidence.
4. Record OS/architecture, `STUDIO_RELEASE_SHA`, exact imported upstream artifact hashes, generated installer SHA-256, logs and short native test outcomes. Upload the **unpublished** installer and logs as GitHub Actions artifacts for later [spec 06](06-release-and-post-release-cleanup.md); never push the installer to a public release from this build job automatically.
5. Hosted Windows runner desktop automation may support some GUI startup checks but cannot be **assumed** to provide a suitable interactive GUI session or fully verify all native dialogs/uninstall behavior. If any required visible Qt/installer check is inaccessible, use a short-lived **interactive Windows x64 cloud VM** (e.g. Azure Windows VM, connected through Remote Desktop from the Mac) to complete **only that remaining smoke** on the same installer SHA. Do not replace this with Wine, a Mac screenshot or an ARM-only Windows VM.

The user does **not** need to borrow a Windows laptop for native Windows x64 packaging. Native GUI limitations, signature requirements and licensing must be reported exactly rather than silently waived. No new broad visual campaign, long soak or large performance qualification is required.
