## Verified starting point and gaps

The 26 October repository snapshot has one Active Run per Controller, persisted Run states, cancellation, staged immutable publication, and restart reconciliation. `MainWindow.closeEvent()` **currently calls `controller.shutdown()` without confirmation**. `shutdown()` requests cancellation and terminates/kills the QProcess; an integration test covers this for a short **Dataset Build**, but not a user-confirmed close or genuine in-flight CNN/RF training. A forced GUI-process death is not equivalent to `shutdown()`: the Worker may outlive its parent. No 600-second real-Worker longevity acceptance is indexed. The Settings and Training UI has no explicit idle-sleep prevention control. Actual OS sleep suspends processing until wake (or until termination), rather than allowing continuous training. These are **coverage and behavior gaps**, not evidence that all interruption paths are defective.

## User-facing contract

1. **Idle close:** Quit normally when there is no Active Run. A completed Run does not trigger a warning; a separately running cancellable Collection Scan must be stopped safely using its existing ownership rules.
2. **Active close:** Before exiting through the window close control, app Quit action or normal Qt quit path, show a native accessible confirmation: **Keep app open** (safe/default) or **Stop Run and Exit**. State the Run/family, that work in progress will be lost, and that **no partially trained Dataset/Model or resumable checkpoint will be kept**. Do not promise continuation after exit. Rejecting/dismissing the dialog leaves Worker, reservation and progress untouched. Repeated close requests must not open stacked dialogs or double-cancel.
3. **Confirmed exit:** Request cancellation, allow bounded cooperative stop, then terminate/kill if necessary. **Only exit once the supervised Worker has stopped**; keep Qt responsive and provide a truthful stopping/failure indication. Never synchronously block the GUI for an unbounded wait. A cooperative stop is `cancelled`; an unclean stop may be `interrupted`—do not rewrite history to look successful. Restore one-Run availability after cleanup/restart. Reuse existing Run status UX and `alp-ui` components; do not edit the HTML prototype.
4. **All-or-nothing artifact rule:** An *incomplete* Run loses its private stage and any unfinished/uncommitted Model/Dataset, including internal intermediate training checkpoints. Nothing is auto-resumed/retried. Already-published, verified **earlier** Datasets/Models, inputs, presets, and Run history remain untouched. If publication was **fully committed** before the interruption, retain the valid immutable artifact and reconcile its status from durable evidence; never delete it just to satisfy a blanket “rollback.” Atomic publication, receipt and crash boundaries must stay consistent.
5. **Abrupt exit:** An OS kill, GUI crash, power loss or system shutdown cannot show a confirmation. Ensure an orphan Worker **cannot continue to commit a new artifact after losing its owning GUI session**. Use a narrowly scoped, cross-platform lifetime/supervision check and pre-publication guard; verify the actual behavior on macOS and Windows. Clean orphaned staging **after the Worker has stopped**, on safe restart/reconciliation. Immediate disk cleanup at the instant of power loss is impossible and must not be promised; do not delete files belonging to a still-live Worker or another instance. Do not introduce global multi-instance locking without a separately established requirement.

## Optional Keep computer awake — app-wide UX and power ownership

1. **What it does:** Provide an explicitly opt-in **Keep computer awake** on/off toggle, **off by default**, usable whenever Trainer is open, with or without an Active Run. When successfully enabled, request protection against **automatic system idle sleep** for the life of the running GUI (including while training or scanning); keep the **display free to dim/turn off**. This is an **application preference**, not a CNN/RF hyperparameter, preset field, Model/Run artifact setting, or automatic side effect of starting a Run. Switching off, exiting normally, or losing the GUI process releases the assertion. No hidden Worker-owned inhibitor.
2. **Placement:** The existing prototype's `settingsPage` (`app.js`, approx. line 275) already establishes the Settings layout, but depicts no power control. Add a small **Power / long-running work** card **below** the native Settings binding/reading cards. Show the same toggle, status, and compact `alp-ui.HelpHint` **near the Start Training action** in the existing `TrainingPage._build_start_card` (prototype `trainPage`, approx. line 254), visible without expanding More settings and in narrow layouts. Both are controls of **one shared app-wide state**: a change on either page updates the other immediately; the Run continues if switched off mid-training. Follow source-first prototype review and actual `alp-ui` Showcase; **do not edit** the HTML prototype or move the primary Start Training CTA. Include native Settings/Train screenshots, focus/keyboard operation and explicit On/Off/Unavailable state.
3. **Preference and failure:** Persist the user's choice in **machine-local Application Settings**, initial default off. The current `SettingsStore` strictly validates schema v2: perform compatible migration, retaining existing Collection binding and accepting older settings; no silent destructive reset. On startup, reacquire protection only if the stored preference is enabled. Never display **On** merely because the preference says so: failed/unsupported OS acquisition must show **Not active** with a plain error and let the user retry or disable it; avoid fictitious protection. Keep state changes idempotent, synchronized across pages, and safe through repeated opens, startup failures, and shutdown. A failed preference write must not misrepresent the effective OS state.
4. **Native platform owner:** Implement one small GUI-process lifetime manager (application/infrastructure, not scientific toolbox) behind a mockable OS adapter. On macOS use an idle-system-sleep power assertion (e.g. `IOPMAssertionCreateWithName` / `kIOPMAssertionTypePreventUserIdleSystemSleep` with matching release); on Windows use `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` and clear it with `ES_CONTINUOUS` **on the owning thread**. Do not request display wake, Away Mode, admin elevation, external services, shell-wide power-plan changes, or bundled third-party wake utilities. Verify installed-app behavior on both actual OSes; ensure abnormal GUI process termination drops its owned inhibition. Use 05d's local diagnostics where available, with no sensitive machine details.
5. **Limits and actual sleep:** Explain that this helps against **inactivity-based sleep**, **not** closing the lid, choosing Sleep, shutdown/logout, low battery, system updates or OS policy. Users may still close the laptop at their own risk. If the computer really sleeps, CPU training **pauses**; on wake it may continue if GUI/Worker survived, but never claim guaranteed survival or progress through sleep. If interrupted, apply the Run recovery/immutable rollback requirements above. A suspend/resume time gap by itself must not be recorded as successful training or automatically discard an otherwise healthy Worker. Display battery-use caution without repeatedly interrupting the user with dialogs.
6. **Plain-language help:** Add a short **Keep computer awake** entry to the existing in-app Wiki and a concise, focusable HelpHint next to both toggles, with a link to the entry. Suggested text: **“When this is on, Trainer asks your computer to stay awake while the app is open. Your screen can still turn off. It may use more battery. Closing the lid or putting the computer to sleep yourself can still pause training.”** One canonical short explanation, reused rather than separate contradictory copies; no new help-navigation framework.

**Verification owners:** `UT-POWER-001` owns preference migration and adapter state/failure decisions; `IT-POWER-001` owns the two native synchronized toggles, Wiki/HelpHint, persistence, accessibility and real-QProcess Run independence; `IT-POWER-002` owns actual macOS/Windows idle-inhibition acquisition/release and fault/GUI-death cleanup. Their concise rows live in the [test indexes](../UNIT_TESTING.md) and [integration behaviors](../INTEGRATION_TEST_BEHAVIORS.md); do **not** fold a 10-minute wait into these normal tests. A deliberate OS suspend/wake or lid-close experiment is **manual, opt-in platform qualification**, not an ordinary CI test or a guarantee of preventing forced sleep. Initial macOS verification belongs to 05g; requalify Windows behavior in 07 and installed-app behavior in 06/07, without claiming unexecuted platform evidence.

## Ten-minute test harness and platform matrix

- **Execution cadence:** `IT-RUN-009` is a **periodic, explicitly invoked durability test**, not a routine test for every spec, commit, or ordinary CI run. Execute it once for initial 05g acceptance; afterwards rerun it only in dedicated occasional soak rounds or when a specific change warrants long-duration requalification. Other specs must not be blocked merely because this soak was not rerun. Mark it `pytest.mark.soak`, register the marker, and **exclude it by default** from ordinary unit/integration/CI runs. Provide one explicit command, e.g. `pytest -m soak tests/integration/test_long_running_runs.py -q`; enforce exclusion rather than merely labeling the test. Keep interruption/dialog cases in the normal focused integration suite.
- Obtain a **genuine training result**, not a sleeping fake Worker or fabricated Model. Use existing supervised QProcess and deterministic real WAV fixtures, with **test-only controlled pacing at actual Worker progress boundaries** if the normal minimal workload finishes too quickly. Prefer existing `--worker-step-delay` where reliable; otherwise introduce the smallest explicitly gated test pacing seam. Production default must remain zero and scientific inputs/outputs unchanged. Use a monotonic clock and a finite, generously bounded timeout; wait by pumping the Qt event loop, not `time.sleep(600)` in the GUI/test thread.
- Sample responsiveness (event-loop heartbeat and responsive UI actions), progress, peak resident memory, process count, open handles where measurable, staging/log bytes and CPU/resource trends at intervals. Report numerical observations and baselines rather than hardcoding arbitrary machine-specific performance limits. Assert no unbounded UI event queue or logging growth, no stale Worker after terminal status, no file-handle/process accumulation after a second Run, and correct artifact checksums. A ten-minute pass **does not establish overnight/long-hours reliability**; optional longer soak and suspend/wake probes may be reported separately without pretending they ran.
- Run focused tests on a native macOS development checkout first; tests must be **portable to actual Windows**, with genuine Windows child-process termination/path behavior requalified in [07](07-windows-release-and-installer.md). Installed-app Worker, sleep/wake and OS logout behavior are platform qualification concerns for [06](06-macos-release-and-installer.md)/07; report untested systems honestly. Do not use offscreen Qt, Linux emulation, CI mocks or sibling repo availability as evidence of passing native Windows/macOS UX.

## Sequence and exit

First add failing tests for the close decision, child-lifetime boundary and power preference/OS adapter; then implement the smallest Qt/Controller/Worker and app-level power changes, verify staged rollback versus valid completed publication, and run the short tests. Run the explicit ten-minute soak **after** short tests pass. Recheck existing `IT-RUN-*`, `IT-TRAIN-*` cancellation/publication tests and 05d diagnostic behavior; do not duplicate their indexed definitions or modify scientific libraries without evidence.

**Exit:** a user cannot accidentally close an active training session; intentional close safely stops it without a resumable checkpoint or partial output; forced owner loss cannot cause later orphan publication; restart accurately reconciles history; an actual 600-second supervised scientific Run completes, remains responsive and reloads; optional native keep-awake controls accurately acquire/release automatic idle-sleep prevention without pretending to override forced sleep. Record per-platform commands, measured duration/resources, hashes, limitations, native visual evidence, and clean commit SHA in the existing evidence ledger. Only a real executed result counts as accepted.
