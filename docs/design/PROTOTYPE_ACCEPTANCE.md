# UX acceptance

For **Train**, existing native Python UI and genuine screenshots are the design baseline. For **new Studio/Detect screens**, the accepted ST-01 interactive prototype defines navigation, hierarchy, wording, state transitions and controls; the installed `alp-ui` Showcase and public API define Qt component behavior and theme.

Prototype acceptance requires: all matrix states reachable; no dead actions; easy navigation back to Studio; no loss of draft state on ordinary switching; responsive desktop layout and keyboard focus; concise researcher-facing HelpHints and guide text; clear recording inclusion and Model errors; recording-specific interval data; validation that gates detection readiness; independent original/refined Results; exports driven by the frozen selected intervals; a visible destination and Show in folder after success.

Use production-ready product language throughout. One unobtrusive banner states that the interface uses example data and performs no real processing. Do not repeat Demo/local/native disclaimers or expose developer notes, stage references, speculative APIs or roadmap commentary in product surfaces. Keep simulation-only selectors together in the separate collapsed **Prototype controls** panel. Treat scientific configuration numbers as illustrative rather than approved defaults.

During native stages, compare actual Qt screens against the accepted prototype and native Train reference. Review normal/narrow widths, empty/loading/error/cancel/completed states, focus order, accessible names, theme/assets and genuine work/result values. Save native screenshots and report deviations for owner approval. Browser interaction tests do not establish scientific or native integration correctness.
