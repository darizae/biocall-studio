# Upstream-first changes to `bioacoustics-dl-toolbox` or `alp-ui`

**Read only when the active Train/Detect stage identifies a concrete missing or defective scientific-library API in `../bioacoustics-dl-toolbox`, or native UI primitive in `../alp-ui`.** This authorizes **targeted code fixes and improvements in the library itself**, with local testing and a **real library Git commit**, instead of hiding library defects behind consumer-only monkeypatches, copies, or workarounds. The sibling `../alpaca-pipelines` remains a separately owned reference; this permission is not permission to rewrite the Trainer UX, add prediction, or silently change pipeline algorithms.

## Decide where the fix belongs

- **Toolbox upstream:** shared CNN model, preprocessing, trainer, checkpoint, numerical correctness, stable serialization, or genuinely reusable RF feature helper is faulty or missing. First reproduce the failure through the **public toolbox API**. A supported extension can be developed here when it is scientifically reusable and does not break existing callers.
- **BioCall Studio downstream:** Train and Detect Collection, Run, Result and Export contracts, Qt navigation/layout, Worker lifetime, app-specific configuration and adapters stay in their owning application workflow. Put only adapters here, not duplicated scientific algorithms.
- **`alp-ui` upstream:** a genuinely reusable missing public widget primitive, accessibility behavior or theme bug belongs in the library. App-specific layout, labels, navigation and workflow validation remain in BioCall Studio. Verify existing public exports/showcase before proposing new components; do not monkeypatch private `alp-ui` internals.
- **`alpaca-pipelines` reference:** its orchestration/RF code must be inspected for behavior, but importing/copying code blindly or changing this repo as a side effect is not the toolbox workflow. Resolve ownership explicitly when a bug is actually in that layer. **Do not alter `../alpaca-pipelines` merely to make the Trainer pass.**

## Required procedure for a pertinent upstream change

1. **Preflight both repositories:** inspect `git status --short --branch` and HEAD SHAs in **Trainer** and **toolbox**. Do not discard existing changes or overwrite someone else's branch. Record the source failing behavior, scope, dependency and public API. Create a focused toolbox branch, e.g. `fix/<scientific-issue>` or `feat/<scientific-capability>`; keep BioCall Studio work on its owning `detect-stNN-purpose` (or existing Train stage) branch. If the toolbox checkout is absent, not writable, or has conflicting changes, record the blocker instead of vendoring it or silently falling back to another package.
2. **Test upstream first:** add a failing toolbox unit or integration regression test at the actual public seam using deterministic inputs and meaningful numerical/serialization assertions; implement the smallest sound fix; run focused tests, appropriate broader toolbox tests, lint/type checks and any existing compatibility tests. Do not weaken tests or change defaults/serialization compatibility without an explicit versioned migration and updated Trainer contract.
3. **Commit upstream:** inspect `git diff --check`, stage only scoped source/tests/docs, and `git commit -m "fix: <specific toolbox behavior>"` (or accurate `feat:` subject). Record the **actual full toolbox commit SHA**, branch, clean tree and test commands/results. An upstream SHA from a ZIP or a claimed commit without `.git` evidence is not proof. **Do not force-push, rebase, merge, or publish the library automatically. After explicit owner review, a **local-only** library branch → library `main` merge is permitted; record resulting real SHA. Never push.**
4. **Reinstall in the Trainer environment:** use the Trainer's existing `.venv` and the toolbox's actual build metadata. On macOS, from the Trainer repository root, the typical command is:

   ```bash
   .venv/bin/python -m pip install -e ../bioacoustics-dl-toolbox
   .venv/bin/python -c "import bioacoustics_dl_toolbox as m; print(m.__file__)"
   .venv/bin/python -m pip show bioacoustics-dl-toolbox
   ```

   Adjust the last command to the verified distribution name if different. Verify the import resolves to **the separate local toolbox checkout**, not `../alpaca-pipelines/src/bioacoustics_dl_toolbox`, an old wheel, or a vendored copy. In editable mode Python may reflect code changes immediately, but explicitly rerun the install/import check to validate metadata and dependencies. Never use a global `pip`.
5. **Retest downstream:** run the affected **real** Trainer scientific unit/integration cases in the actual `.venv`, including a real trained CNN/Model structural reload for checkpoint changes and precise feature-schema tests for any RF change. Verify other unchanged consumers where practical. Capture the dependency SHA/version and any resolved config changes in exported Model provenance. A Detect stage may add **only the inference/scoring specifically owned by its active ST-07 or ST-09 spec**; unrelated Train changes and unverified algorithms remain forbidden.
6. **Lock for shipping:** update the Trainer's declared dependency/version constraints and reproducible lock/build provenance as appropriate. Editable path installs are **development-only**; macOS/Windows releases must package a validated wheel built from an identified, **committed** toolbox revision. Run clean-environment and installed-app checks independent of sibling source paths. Coordinate any backwards-incompatible API/format change with a versioned artifact/compatibility policy; do not silently mutate prior Models or presets.
7. **Report both repositories:** provide the Trainer branch/commit SHA **and** toolbox branch/commit SHA, tests and logs for each, reinstall command, actual `bioacoustics_dl_toolbox.__file__`, selected package version/wheel digest when applicable, and blockers. A Trainer-only green suite is **not sufficient** to close an upstream change. If the upstream fix cannot be committed/tested, report the relevant spec as blocked rather than quietly patching downstream.

This permission is **scoped to pertinent science or UI-library changes needed by the active spec**. Prefer a small compatible change over broad refactoring; do not open the entire upstream repository or change unrelated APIs. The owner still controls upstream publishing/releases and overall Trainer spec acceptance.

## Separate `alp-ui` branch procedure (only when a real public-component gap is verified)

1. Inspect the installed library version, public exports, docs and relevant Showcase/component tests. Confirm why standard Qt + existing public `alp-ui` cannot satisfy the active screen; **do not** add a component for a single app-specific caption or layout preference.
2. In `../alp-ui`, inspect Git status/HEAD; create `fix/<specific-ui-issue>` or `feat/<small-public-component>`. Add a failing component/accessibility test, implement and run library-targeted plus appropriate full library checks. Commit the library separately and record its actual SHA.
3. After explicit review, integrate the upstream branch into **local** library `main` only; never push. Reinstall/select the verified UI package in BioCall Studio's project `.venv`, record `alp_ui.__file__`/version/actual SHA, and run owning native Qt/keyboard/theme/compact-window integration cases plus full feasible ordinary BioCall Studio suites before downstream commit.
4. If the library/API or native platform is unavailable, keep its owning stage blocked, document the smallest unresolved dependency, and do not compensate using private monkeypatches, fake controls or undocumented component APIs. Public release still requires reproducible pinned wheels, not an editable checkout.
